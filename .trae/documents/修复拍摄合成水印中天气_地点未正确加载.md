## 现象与结论

* 预览层水印：天气与地点均正常；拍摄后合成图：海拔/方位角/经纬度/制作单位正常，天气显示“获取失败”，地点显示“获取中”。

* 从日志看，逆地理与天气接口在拍摄前已成功返回：`AmapService` 的 regeo 与 weather 请求、解析均成功（log.md:11–16）。随后触发了水印缓存刷新（log.md:17,20）。

* 合成阶段仍出现天气/地点的占位文案，推断为拍摄链路读取到“缓存占位值”或在 provider 绑定/刷新时序上未命中有效值。

## 数据传递流程

* 预览 UI（`entry/src/main/ets/views/WatermarkOverlay.ets`）

  * 绑定 Provider：`photoManager?.setLocationWeatherProvider(() => AmapService.fetchLocationAndWeatherAuto())`（WatermarkOverlay.ets:48–49）。

  * 拉取并填充：`loadLocationAndWeather()` 内置前置态“获取中”，成功后写入 `watermarkInfo` 并调用 `photoManager.refreshWatermarkCachesImmediately()`（WatermarkOverlay.ets:207–219,214）。

* 位置/天气服务（`entry/src/main/ets/services/AmapService.ets`）

  * 逆地理 -> 取 `adcode` -> 天气；成功即缓存（位置24h、天气5min），失败返回占位（AmapService.ets:68–127,129–187,189–209）。

* 拍摄链路（`entry/oh_modules/camera/src/main/ets/cameramanagers/PhotoManager.ets`）

  * Provider 注入：`setLocationWeatherProvider`（PhotoManager.ets:181–186）。

  * 动态信息预热：`prewarmWatermarkInfo()` 内部通过 `getWeatherInfo()/getLocationInfo()` 使用 provider 或回退（PhotoManager.ets:206–229,596–615,620–639,641–665）。

  * 取水印信息：`getWatermarkInfo()` 若缓存过期则再次预热并返回（PhotoManager.ets:551–590）。

  * 生成/混合/保存：`processSavedAssetWithWatermark()`（PhotoManager.ets:728–751）。

  * 当 provider 未命中或值为空时，`getWeatherInfo()` 回退为“获取失败”（PhotoManager.ets:612–615）；`getLocationInfo()` 回退为“获取中”（PhotoManager.ets:635–639）。这与拍后图片上的显示完全一致，指向“动态信息在拍摄链路读取时仍为占位值”。

## 根因推断

* Provider 绑定时序：PhotoManager 构造时会执行一轮预热，但 provider 是在 `WatermarkOverlay.aboutToAppear` 才绑定；若首轮预热将缓存写入占位值，则 30s TTL 内可能被直接复用，除非刷新成功覆盖。

* 刷新覆盖不稳定：`refreshWatermarkCachesImmediately()` 会清空并重建缓存，但其预热仍依赖 `getWeatherInfo()/getLocationInfo()` 的 provider 调用；若该异步在合成前尚未完成或返回空值，拍摄链路继续使用占位回退。

* 回退文案不一致：天气回退“获取失败”、地点回退“获取中”，导致肉眼差异更醒目（PhotoManager.ets:612–615,635–639）。

## 优化方案

* 方案A：前移 Provider 绑定与统一预热

  * 在页面初始化（Index.ets）立即绑定 provider 并主动预热，避免 PhotoManager 首轮预热写入占位值。

  * 实施点：

    * 在 `Index.ets` 的构造/`aboutToAppear()` 中调用：

      * `this.photoManager.setLocationWeatherProvider(() => AmapService.fetchLocationAndWeatherAuto())`（Index.ets:62 引用的实例）。

      * 紧随其后执行 `this.photoManager.prewarmWatermarkCaches()`（Index.ets:173–185 的前台预热也可复用）。

    * 保持 `WatermarkOverlay` 中现有绑定不冲突（WatermarkOverlay.ets:48–49），但改为兜底而非首次绑定。

  * 优点：简单、改动小，显著降低占位值被缓存的概率。

  * 风险/代价：预热带来极低的首帧异步开销；需确保权限已就绪或容错。

* 统一回退文案：将地点回退也改为“获取失败”，与天气保持一致，减少用户误解（PhotoManager.ets:635–639）。

## 选择建议

* 若希望最小改动且快速稳定：优先选“方案A”。

* 若追求 UI 与拍摄一致性且去除竞态：选“方案B”。

* 若不改 UI，强化拍摄链路鲁棒性：选“方案C”。
